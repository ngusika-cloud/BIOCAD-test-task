# Как я декомпозировал тестовое задание

Это план, по которому я разбил [исходное задание](task-description.md) на проверяемые части и собрал из них готовый продукт. Каждый этап заканчивался рабочим сквозным сценарием.

## 1. Выделить основной сценарий

Сначала я свёл задание к одной цепочке:

1. Открыть приложение и увидеть засидированный план на диаграмме Ганта.
2. Загрузить Excel со своими задачами.
3. Массово изменить план через AI-чат.
4. Сразу увидеть изменения на диаграмме.
5. Открыть задачу, проверить детали и при необходимости отредактировать её вручную.
6. Скачать обновлённый план в Excel.

Эта цепочка стала основой для API, интерфейса, тестов и демо-видео.

## 2. Разбить сценарий на функции

| Часть | Что нужно сделать | Как я проверял результат |
| --- | --- | --- |
| Стартовые данные | Создать тестовый проект на backend | После запуска диаграмма заполнена без дополнительных действий |
| Диаграмма Ганта | Показать задачи, сроки и зависимости | Задачи и связи читаются, масштаб можно менять |
| Карточка задачи | Открывать детали по клику и разрешить ручную правку | Валидное изменение сразу попадает в план |
| Импорт Excel | Принять пять колонок из задания и показать ошибки до изменения плана | Корректный файл импортируется, некорректный не меняет данные |
| Экспорт Excel | Собрать `.xlsx` из текущего состояния | Скачанный файл можно загрузить обратно без потери данных |
| AI-чат | Перевести запрос пользователя в безопасные операции над планом | Команды на перенос, добавление, удаление и смену исполнителя дают ожидаемый diff |
| MCP | Открыть те же операции через stdio-сервер | REST, AI и MCP используют одни правила и одинаково меняют проект |
| Публикация | Развернуть frontend и backend, настроить secrets и CORS | Основной сценарий проходит на публичном URL |

## 3. Отделить расчёты от AI

До подключения LLM я определил модель данных и правила планирования.

- Задача имеет стабильный ID, название, описание, длительность, исполнителей и предшественников.
- Внутренние связи строятся по ID, хотя в Excel и интерфейсе видны названия.
- Scheduler проверяет ссылки, дубли и циклы, затем рассчитывает даты и человеко-часы.
- LLM распознаёт намерение и вызывает типизированные tools. Она не считает расписание и не записывает данные напрямую.

Так ошибка модели не ломает граф зависимостей и не создаёт частично валидное состояние.

## 4. Собрать продукт вертикальными срезами

### Этап 1. Каркас

Я создал `frontend/`, `backend/`, `docs/` и `sample/`, настроил React/Vite, FastAPI, Ruff и pre-commit. Точка готовности: frontend и backend запускаются локально, `/health` отвечает без ошибок.

### Этап 2. Модель проекта

Я добавил модели, seed, in-memory repository, scheduler и проверку графа. Этот слой сначала проверил unit-тестами, чтобы UI и AI не скрывали ошибки в расчётах.

### Этап 3. REST API и диаграмма

Дальше собрал первый полный сценарий: API отдаёт проект, React показывает его на Gantt, карточка задачи читает и меняет данные. На этом этапе продукт уже был полезен без Excel и AI.

### Этап 4. Excel

Импорт разделил на preview и confirm. Пользователь сначала видит ошибки, а план меняется только после подтверждения. Затем добавил экспорт и проверил цикл `импорт → правка → экспорт → повторный импорт`.

### Этап 5. Общие операции и MCP

Все изменения проекта я вынес в один сервисный слой. На нём собрал MCP-сервер. Благодаря этому REST, MCP и будущий агент не разошлись в бизнес-правилах.

### Этап 6. AI-агент

К готовым операциям подключил LangGraph и OpenRouter. Агент получает актуальный контекст, вызывает типизированные tools и возвращает понятный ответ. Отдельно проверил массовые команды, лимиты tool calls и неоднозначные запросы.

### Этап 7. Обратная связь в интерфейсе

Я добавил SSE, историю чата, очистку, статусы запроса, подсветку изменённых задач, а также отображение модели, токенов и стоимости. После этого ответ агента и новое состояние плана стали видны без перезагрузки страницы.

### Этап 8. Публикация и передача

После локальной проверки я развернул frontend и backend, настроил CORS и secrets, затем повторил основной сценарий на публичном URL. В поставку вошли README, тестовый Excel, MP4-демо и roadmap.

## 5. Проверять рисковые места по ходу работы

Проверку я не оставлял на финал. Каждый срез добавлял свой набор тестов.

- Scheduler: цепочки зависимостей, параллельные ветки, неизвестные ссылки, self-dependency и циклы.
- API: CRUD, атомарность и понятные ошибки.
- Excel: валидация колонок, связей и round-trip без потери данных.
- Агент: одиночные и массовые операции, continuation после лимита, ошибки OpenRouter и формат SSE.
- Frontend: production build, импорт, ручная правка, AI-изменения, экспорт и ошибки в интерфейсе.
- Публичная версия: тот же сценарий на Render, что и локально.

## 6. Финальный чек-лист

Перед передачей я проверил, что все пункты из исходного задания закрыты:

- React, FastAPI, MCP и LLM через API используются в рабочем сценарии;
- при открытии есть тестовый план;
- Excel импортируется и экспортируется;
- чат массово меняет план, а диаграмма сразу обновляется;
- задачу можно открыть и изменить вручную;
- публичная версия доступна по ссылке;
- в репозитории лежат README, пример Excel, MP4-демо и [roadmap](ROADMAP_TO_PRODUCTION.md).
